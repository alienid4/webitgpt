1

資料分散

CMDB、掃描結果、帳號盤點、效能紀錄各自存在，欄位命名與完整度不一致。

2

判讀靠經驗

Script 可以查出結果，但誰受影響、要通知誰、風險多高，仍仰賴人工判斷。

3

回報難成形

主管需要一句話摘要與處置建議，現場卻常只有一串 log、CSV 或掃描文字。

導入前的主要痛點：不是沒有資料，而是資料太散、太慢、太難判讀。

From Evidence To Decision

AI 預期效益：讓現場少整理，讓主管快決策。

這套平台不是讓 AI 直接取代維運，而是把「採證」與「判讀」分工。 採證仍由可追溯的 Script、API 與資料來源完成，AI 協助整理脈絡、風險分級與建議行動。

L3 深度檢查

AI 讀取巡檢、效能、拓撲與帳號證據，產出可讀摘要、可能原因、影響範圍與下一步建議。

  • 將多來源資料合併成一段可回報文字。
  • 把「異常」轉成「風險等級與處置順序」。
  • 保留證據來源，避免只靠直覺判斷。

不中斷的保底機制

當 API Key、模型服務或預算不可用，系統退回既有 Script 規則與人工流程。

  • L1 基礎檢查：Script-first。
  • L2 一般判讀：低成本模型或規則摘要。
  • L3 深度判讀：高階模型與預算控管。

時間效益

縮短資料收集、比對與回報文字整理時間。

品質效益

降低漏看關聯系統、通知對象與帳號風險的機率。

治理效益

透過來源標示、成本控管與 debug 模式，提高可稽核性。

Three-Month Introduction Plan

從 4/15 開始，三個月完成可驗收導入。

導入時程以三個月計算，先完成資料與採證基礎，再導入可視化與離線部署， 最後補上 AI 判讀、API Key 治理與正式驗收。

第 1 個月｜4/15 - 5/14

建立基礎資料面

  • 主機與 CMDB 欄位治理。
  • 資產草稿區與匯入驗證。
  • 今日巡檢與基礎 Script 採證。
  • 版本規則與部署流程建立。
第 2 個月｜5/15 - 6/14

完成營運可視化

  • NMON 效能月報與 EOS 摘要。
  • OS/AP 帳號盤點與異常彙整。
  • 核心系統影響圖與通知名單。
  • 離線安裝與 RHEL 9.6 移植驗證。
第 3 個月｜6/15 - 7/14

導入 AI 判讀與治理

  • L1/L2/L3 判讀分級與 fallback。
  • API Key 設定、預算與成本控管。
  • AI-ready 淡金框與 AI 深金框辨識。
  • 驗收文件、操作手冊與交接資料。
最終目標：讓維運從「找資料」進化成「判斷、溝通與決策」。
