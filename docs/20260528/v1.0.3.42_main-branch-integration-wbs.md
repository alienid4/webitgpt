# v1.0.3.42 main 主線整合 WBS

## 目的

將目前文件與功能開發分支的成果，逐步整理到 `main`，讓 GitHub 預設分支成為一致、可下載、可交接的正式入口。

本 WBS 的重點不是一次性硬合併，而是降低主線衝突、避免覆蓋可用版本，並讓每一批整合都有測試與部署驗證。

## 背景說明

目前 `main` 與 `docs/current-architecture-v2` 不是單純快轉關係。直接合併會遇到不同歷史起點與大量 `add/add conflict`，範圍包含：

- `webapp/app.py`
- `webapp/routes/*`
- `webapp/services/*`
- `webapp/templates/*`
- `scripts/*`
- `tests/*`
- 部分文件與 release notes

因此建議採用「main 保持正式主線，從開發分支分批 cherry-pick 或選擇性搬移」的方式，避免一次性合併造成程式碼、安裝腳本或部署流程退版。

## 建議執行順序

1. 文件、報告、zip 先放到 `main`，讓 GitHub 預設分支可下載。
2. 建立程式差異盤點表，不急著合併程式。
3. 確認正式主線後，建立 `integration/main-cleanup`。
4. 分批 cherry-pick 有價值內容。
5. 每批先跑測試，再部署到測試主機驗證。
6. 最後才更新 `main`、tag、release。

## 建議策略

建議不要做全量 merge。

較穩定的做法是：

- `main` 保持正式入口。
- 文件與交付物先上 `main`。
- 程式碼用小批次 cherry-pick 或逐檔搬移。
- 每批都有測試、部署與截圖驗證。
- RHEL 9.6、離線安裝、Mongo/podman 相關腳本最後整合。

這樣能降低主線衝突，也比較符合維運環境的風險控管。
