Before / After

平台要解決的，不只是巡檢，而是決策前的混亂。

webitgpt 將資產、帳號、拓撲、效能與巡檢放到同一個維運工作台。 目標不是多做一張報表，而是讓異常發生時，能快速知道「誰受影響、證據在哪、下一步做什麼」。

  • 離線移植與版本更新高度仰賴現場經驗。

  • 資料先進草稿區，驗證後再進正式資產。
  • 帳號、權限、PAM、owner 可一起盤點。
  • NMON、EOS、核心影響圖與巡檢互相連結。
  • 安裝、patch、RHEL 移植有文件與版本治理。

Function Coverage

重點功能不是全列，而是支撐事件處理的四個能力。

這些功能共同回答四個問題：資產是誰、誰有權限、目前狀態如何、異常會影響誰。

資產治理

CMDB CSV/Excel 匯入、草稿區、欄位驗證、錯誤列回報、正式資產管理。

帳號盤點

OS/AP 帳號、權限、owner、PAM 狀態與異常彙整，補足應用帳號缺口。

效能與巡檢

NMON 日/週/月報、EOS 摘要、L1/L2/L3 巡檢、Script 採證與結果追蹤。

影響分析

核心系統影響圖、關聯系統、主機/IP、Ghost 清單與通知名單匯出。

平台價值不是「功能很多」，而是讓資料能串成同一個維運決策流程。

AI With Guardrails

AI 預期效益：讓現場少整理，讓主管快決策。

AI 不取代維運採證。平台採用分工設計：Shell/Script/API 負責取得事實， AI 負責摘要、風險分級、跨資料源關聯與建議行動。

真正 AI 判讀

  • L3 深度檢查產出風險摘要與建議。
  • 把多來源資料轉成主管看得懂的結論。
  • 深金框表示 AI 已參與判斷。

AI-ready 與保底

  • 淡金框只表示資料可交給 AI 判讀。
  • API 或模型不可用時，Script 規則接手。
  • L1/L2/L3 API Key 依難度與預算分級。

時間效益

縮短資料收集、比對與回報整理時間。

品質效益

降低漏看關聯系統、帳號權限與通知對象的風險。

治理效益

透過來源標示、預算控管與紀錄，提高可稽核性。

Operating Model

導入治理建議：把平台當成共同維運流程來經營。

webitgpt 的價值來自跨單位資料與維運流程的整合。導入時建議先把資料來源、 採證方式、權限、成本與版本流程定義清楚，讓平台成為共同協作的工作台。

治理面向 目的 建議做法
CMDB 資料品質 讓資產、拓撲、帳號與 AI 判讀能建立在一致欄位上。 建立資料負責窗口，定義必填/選填/允許空值與錯誤列處理。
Script 採證維護 保留可追溯的事實來源，讓 AI 判讀有可靠依據。 nmap、NMON、SSH、WinRM、帳號查詢納入測試與版本紀錄。
AI 判讀治理 讓 AI 協助摘要與分級，同時保留高風險操作的控管。 停機、停帳、修補與異動保留人工覆核、來源證據與回滾流程。
API Key 與成本 讓 AI 使用可預期、可追蹤，也能控制成本。 L1/L2/L3 分級，超額時自動降級或停用，保留 debug log。

Promotion Readiness

推廣建議：先建立共同成功條件，再擴大使用範圍。

推廣時建議把平台定位成共同維運治理工具，由各單位一起定義資料、流程、 權限與驗收方式，讓既有經驗可以被系統化累積。

建立資料窗口

每個系統、主機、AP 帳號、備份與個資欄位建議有對應維護窗口。

對齊標準欄位

共同定義 CMDB 與帳號盤點必要欄位、選填欄位與空值規則。

對齊使用流程

匯入、草稿審核、異常確認與追蹤關閉，建議有共同操作流程。

落實最小權限

讀取、匯出、巡檢、管理、API Key 設定必須分角色。

定義 AI 使用規則

明確區分 AI 判讀、AI-ready 與需要人工覆核的情境。

建立驗收指標

匯入成功率、巡檢覆蓋率、NMON 覆蓋率、拓撲正確率、異常追蹤率。

推廣重點是讓既有維運經驗、資料與流程能被更穩定地串起來，形成可持續累積的共同工作方式。
