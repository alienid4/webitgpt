## 本專案內建工作技能摘要

接手者不一定擁有原工作環境的 `SKILL.md`，所以請把本節視為 webitgpt 的固定工作規則。若 VSCode Codex 有自己的 skill 機制，也應優先套用這些規則。

### webitgpt-auto-dev-loop

使用時機：

- 使用者要求「做」、「改版」、「開發」、「修復」、「用 auto dev loop」。
- 任務涉及功能實作、測試、部署、release。

工作方式：

- 先讀 repo 狀態與相關程式碼。
- 拆成小步驟：修改、測試、部署測試主機、確認畫面或 API。
- 不停在建議，能做就直接做。
- 重大或高風險項目才回頭請使用者決策。

### webitgpt-release-patch

使用時機：

- 版本 bump。
- patch / release / GitHub Release。
- 離線 patch TAR。
- 下載點、SHA256、install command。

固定規則：

- 版本只能 `v1.0.X.Y`。
- 每段最多 `99`。
- 檔名版本在前、功能在後。
- TAR layout 必須維持 v1.0.3.89 相容。
- TAR 內固定 `install.sh`。
- 公司測試版本必須上 GitHub Release。
- 不能把 data、logs、backup、secrets、upload、真實清冊包進 release。

### webitgpt-offline-install

使用時機：

- 新機一鍵安裝。
- 離線移植。
- RHEL / Rocky / Debian 安裝問題。
- MongoDB / Podman / full offline package。

固定規則：

- 公司 Linux 可能不能上網。
- offline installer 不可在安裝時才去抓 internet dependency。
- RHEL 不能混入 Rocky release RPM。
- protected packages 不可硬裝或替換。
- podman / MongoDB 失敗時要清楚說明下一步，不可讓 bootstrap 直接撞 Mongo connection refused。

### webitgpt-ai-handoff-debug

使用時機：

- 交接給公司 GPT / VSCode Codex。
- 產生 debug bundle。
- 使用者說「你不能連公司環境，要我提供什麼」。

固定規則：

- 不猜環境。
- 產出一次性診斷指令。
- 輸出到 `/tmp`。
- 預設去敏化。
- 回傳資料只用 count、status、hash、分類統計、HTTP code、version。

### webitgpt-ai-judgement-ui

使用時機：

- API Key / AI 判讀。
- L1 / L2 / L3。
- Script fallback。
- AI-ready / AI judgement UI。

固定規則：

- Shell 負責採證，AI 負責判讀。
- API / AI 不可用時要有 Script / Rule fallback。
- AI-ready 用淡金框；真正 AI 判斷用深金框。
- 畫面上要清楚區分 Script、Rule、API Key、AI。
- 不要讓使用者誤以為所有結果都是 AI 判斷。

### cathay_ai_role

使用時機：

- 公司規範、治理、SQL Server、Swagger/OpenAPI、no-PHP、內部 GPT。

固定規則：

- webitgpt 現況是 Flask + MongoDB，不能硬套 Node.js 範本。
- 可逐步補 OpenAPI，不要一次重寫所有 API。
- 新 API 盡量走 `{ ok, data/error }`，舊 API 保相容。
- 未來可規劃 MSSQL migration，但不要在小 patch 裡硬改資料庫。

### webitgpt UI 操作規則

這是使用者反覆要求的產品規則，優先級很高：

- 預設不展開大表格。
- 預設只顯示摘要、搜尋、篩選、顯示全部入口。
- 點數字卡要能自動過濾到對應資料。
- 批次治理、debug、自檢、低頻功能要收合。
- 狀態欄放第一欄。
- 操作完成要顯示結果與筆數。
- 長清單用可搜尋下拉，不要把全部攤開。
- 說明文字用小問號或展開，不要佔版面。
- 如果修一個 UI 模式，要順手檢查同類型頁面是否也有同樣問題。

使用者反覆指出：系統功能很多，但畫面不能把人淹沒。請遵守：

- 預設不要直接顯示大表格。
- 預設只顯示摘要、搜尋入口、篩選條件與必要的下一步。
- 使用者搜尋、篩選、點數字卡或按「顯示全部」後才展開清單。
- 批次治理、debug、自檢、低頻維護功能預設收合。

- 長清單用可搜尋下拉選單，不要直接列出一大串。
- 狀態要放第一欄，讓人一眼看出使用中、草稿、下線、待刪除、待檢。
- 操作完成後要顯示結果與筆數，例如「已更新 43 筆」或「轉正式 2 筆」。
- 點數字卡應自動套用對應篩選，不應只是裝飾。

## 資料與敏感資訊規則

不要把以下內容提交到 git、GitHub Release、文件、log 或 debug bundle：

- 真實 IP、主機名稱、FQDN、資產編號、系統代號。
- 人名、Email、電話、部門詳細資訊。
- Token、API key、密碼、cookie、session、private key。
- 原始 Mongo dump、原始 CMDB Excel、原始 log。
- 截圖中可識別的公司資料。

需要查公司環境問題時，請產出去敏化診斷指令，輸出只保留：

- count。
- status。
- HTTP code。
- version / patch id。
- 短 hash。
- 分類統計。

不要要求使用者貼原始資料。

## 公司環境問題處理規則

如果使用者說「數字不對」、「某系統只有 3 台但應該 6 台」、「資料品質還是異常」、「公司環境跟測試環境不同」，不要直接猜。

正確流程：

1. 先確認目前程式邏輯。
2. 產出一段可以在目標主機執行的診斷 shell / Python。
3. 診斷輸出預設寫到 `/tmp`。
4. 輸出內容必須去敏化。
5. 讓使用者回傳去敏化 JSON 或摘要。
6. 根據資料修正，並補 regression test。

## Release 與版本規則

版本規則：

- 只能用 `v1.0.X.Y`。
- 每段最多 `99`。
- 修改 app runtime 行為要 bump version。
- 每改一版要 commit。
- 公司要測試的 patch 必須放 GitHub Release。

Release TAR 命名：

```text
webitgpt_v1.0.X.Y-patch-<feature-slug>_<yyyymmddHHmm>.tar.gz
```

Release TAR layout 必須保持相容：

```text
webitgpt_v1.0.X.Y-patch-<feature-slug>_<timestamp>/
  copy_commands.md
  install.sh
  PACKAGE_MANIFEST.txt
  payload/
  RELEASE_NOTE.md
  ROLLBACK.sh
```

TAR 內固定使用 `install.sh`。不要改名。

`install.sh` 必須能用 `sh install.sh` 或 `bash install.sh` 執行，開頭要保留：

```sh
#!/usr/bin/env sh
if [ -z "${BASH_VERSION:-}" ]; then
  exec bash "$0" "$@"
fi
set -euo pipefail
```

公司 Linux 主機可能不能上網。patch install 不應做 pip install 或任何網路下載。

## 公司主機無 Git 的回復機制

公司測試或正式主機可能沒有 git，也不應依賴 git 直接回復。因此接手者必須把 GitHub Release、patch rollback、目標主機備份與 VM snapshot 視為同一套安全流程。

固定規則：

- 公司主機只安裝 GitHub Release 下載的 TAR，不安裝散檔。
- 裝 patch 前先做 VM snapshot。
- 裝 patch 前再備份 `/opt/webitgpt`。
- patch 壞了先執行 TAR 內的 `ROLLBACK.sh`。
- rollback 還是不正常時，還原 VM snapshot。
- 不要在公司主機直接手改程式後再回頭補 git；所有可測版本都要先從 repo 產生 release。

Snapshot 命名建議：

```text
webitgpt_before_v1.0.X.Y_YYYYMMDD_HHMM
```

公司主機安裝前備份指令：

```bash
sudo tar -czf /tmp/webitgpt_opt_backup_$(date +%Y%m%d_%H%M%S).tar.gz /opt/webitgpt
```

安裝後基本確認：

```bash
curl -sS http://127.0.0.1:8002/health
systemctl status webitgpt --no-pager
```

壞掉時的順序：

1. 停止繼續疊 patch。
2. 記錄目前版本、patch id、錯誤畫面或去敏化 log。
3. 執行該 release TAR 內的 `ROLLBACK.sh`。
4. 再確認 `/health` 與 service。
5. 若仍失敗，還原 VM snapshot。
6. 回 repo 用最小 patch 修復，不要在公司主機直接改散檔。

接手者需要向使用者確認：

- 這次安裝前是否已做 VM snapshot。
- snapshot 名稱。
- 是否已備份 `/opt/webitgpt`。
- 目前安裝的是哪個 GitHub Release。
- 目前 `/health` 回傳的 version / patch id。

## 小修與大修判斷

小修通常包含：

- 文字、標籤、提示語、按鈕名稱。
- CSS spacing、預設收合、欄位順序。
- 單一頁面的低風險 UI 呈現。
- 不影響資料寫入的查詢條件微調。

小修可快速流程：

1. focused test。
2. 檢查頁面或 API。
3. 打包 patch。
4. 部署測試主機。
5. `/health` 與相關頁面驗證。
6. commit / push / GitHub Release。

大修包含：

- 匯入、轉正式、批次治理、資料品質規則。
- 開門檢查、L1/L2/L3 runner、SSH/WinRM/AIX/AS400。
- 系統拓撲、核心影響圖、關聯資料。
- 權限、Token、API Key、PAM、採集帳號。
- 安裝、離線部署、MongoDB、Release layout。
- 安全、敏感資訊、debug bundle。

大修要補：

- focused tests。
- full pytest。
- 敏感資訊檢查。
- 測試主機部署驗證。
- release note。
- rollback 風險說明。

## 已知風險與下一步

優先注意：

- 大量資料頁面的預設查詢與渲染速度。
- 資產總數、可自動彙整、人工作業判斷的統計口徑要一致。
- 系統名稱正規化與別名治理，例如同義字、錯字、簡繁或常見誤寫。
- 開門檢查應只顯示可巡檢平台，不應把端點設備、網路設備、VMware host 混入巡檢候選。
- 匯入後的資產應能進入今日巡檢的候選口徑，但前提是平台、狀態、連線方式與帳號條件足夠。
- 系統關聯覆蓋明細應用搜尋式下拉，不要預設攤開全部。
- 資料品質頁的異常項目要能點進去自動過濾，並支援同類型批次套用建議。
- 文件與手冊要避免敏感資料與亂碼。

## 接手者自我檢查清單

接手者開始前要能回答：

- 目前 patch id 是什麼？
- 最近 GitHub Release 是哪一版？
- 這次需求是小修還是大修？
- 會碰到資料寫入、匯入、巡檢、拓撲、install、權限或安全嗎？
- 需要 focused test 還是 full pytest？
- 需要部署測試主機嗎？
- 需要 GitHub Release 嗎？
- 是否有敏感資料外洩風險？
- 是否會破壞 3.89 相容 patch TAR layout？

## Definition of Done

接手後每次完成任務，至少要回報：

- 修改內容。
- 版本是否變更。
- 測試與驗證結果。
- 是否部署測試主機。
- 是否建立 GitHub Release。
- 下載位置。
- 已知風險。

如果無法驗證，必須明講原因與替代檢查。
