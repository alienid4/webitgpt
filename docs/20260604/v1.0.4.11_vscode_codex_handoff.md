# webitgpt VSCode Codex Handoff

版本：v1.0.4.11
日期：2026-06-04
用途：交接給在 VSCode 內執行的 Codex / GPT coding agent，讓它可以接續維護 webitgpt。

## 先讀這段

你正在接手的是 webitgpt，一套 Flask + MongoDB 的 IT 巡檢、CMDB、資產治理與核心系統影響圖平台。這份文件是接手入口，不是完整規格書。請先讀 repo 狀態，再動手。

接手原則：

- 先讀程式碼、設定、文件與測試，再決定修改方式。
- 不猜公司環境問題；無法直接查環境時，先產出「可去敏化」的一次性診斷指令給使用者執行。
- 小修可快速驗證；資料匯入、巡檢、拓撲、安裝、權限、安全與 release 流程不可省略驗證。
- 每個版本變更都要進 git。
- 公司測試必須能從 GitHub Release 下載 patch。

## 接手後第一件事

在 VSCode terminal 進入 repo root 後執行：

```powershell
git status --short
git branch --show-current
git pull --ff-only
python -m pytest -q
```

如果測試太久且只是文件或小 UI 文字調整，可先跑 focused test，但最後發 GitHub Release 前要依風險補足驗證。

## 產品功能地圖

webitgpt 目前主要功能：

- CMDB / Excel / CSV 匯入。
- 資產管理：查詢、篩選、編輯、狀態治理、批次處理。
- CMDB 資產池：資料、軟體、人員與待分類資料視圖。
- 資料品質：缺欄、平台分類、連線方式、掃描與 CMDB 差異。
- 今日巡檢 / 開門檢查：依系統與平台分組，顯示可巡檢、待檢、待補條件。
- L1 / L2 / L3 巡檢：L1 快速檢查、L2 盤點、L3 深度檢查。
- 核心系統影響圖：核心、關聯系統、主機/IP 三層關係。
- 系統關聯覆蓋明細：用來看每套系統 owner、通知、Port、關聯圖覆蓋狀況。
- IPAM / 網段管理。
- 帳號盤點、AP 帳號、PAM / owner 規則。
- 效能月報與 NMON 資料。
- 系統管理：Token、採集帳號、規則、健康檢查、備份、發布、稽核等。

## 目前最重要的 UX 規則

使用者反覆指出：系統功能很多，但畫面不能把人淹沒。請遵守：

- 預設不要直接顯示大表格。
- 預設只顯示摘要、搜尋入口、篩選條件與必要的下一步。
- 使用者搜尋、篩選、點數字卡或按「顯示全部」後才展開清單。
- 批次治理、debug、自檢、低頻維護功能預設收合。
- 備註說明不要佔整行大段文字；用小型說明符號或可展開區塊。
- 長清單用可搜尋下拉選單，不要直接列出一大串。
- 狀態要放第一欄，讓人一眼看出使用中、草稿、下線、待刪除、待檢。
- 操作完成後要顯示結果與筆數，例如「已更新 43 筆」或「轉正式 2 筆」。
- 點數字卡應自動套用對應篩選，不應只是裝飾。

## 資料與敏感資訊規則

不要把以下內容提交到 git、GitHub Release、文件、log 或 debug bundle：

- 真實 IP、主機名稱、FQDN、資產編號、系統代號。
- 人名、Email、電話、部門詳細資訊。
- Token、API key、密碼、cookie、session、private key。
- 原始 Mongo dump、原始 CMDB Excel、原始 log。
- 截圖中可識別的公司資料。

需要查公司環境問題時，請產出去敏化診斷指令，輸出只保留：

- count。
- status。
- HTTP code。
- version / patch id。
- 短 hash。
- 分類統計。

不要要求使用者貼原始資料。

## 公司環境問題處理規則

如果使用者說「數字不對」、「某系統只有 3 台但應該 6 台」、「資料品質還是異常」、「公司環境跟測試環境不同」，不要直接猜。

正確流程：

1. 先確認目前程式邏輯。
2. 產出一段可以在目標主機執行的診斷 shell / Python。
3. 診斷輸出預設寫到 `/tmp`。
4. 輸出內容必須去敏化。
5. 讓使用者回傳去敏化 JSON 或摘要。
6. 根據資料修正，並補 regression test。

## Release 與版本規則

版本規則：

- 只能用 `v1.0.X.Y`。
- 每段最多 `99`。
- 修改 app runtime 行為要 bump version。
- 每改一版要 commit。
- 公司要測試的 patch 必須放 GitHub Release。

Release TAR 命名：

```text
webitgpt_v1.0.X.Y-patch-<feature-slug>_<yyyymmddHHmm>.tar.gz
```

Release TAR layout 必須保持相容：

```text
webitgpt_v1.0.X.Y-patch-<feature-slug>_<timestamp>/
  copy_commands.md
  install.sh
  PACKAGE_MANIFEST.txt
  payload/
  RELEASE_NOTE.md
  ROLLBACK.sh
```

TAR 內固定使用 `install.sh`。不要改名。

`install.sh` 必須能用 `sh install.sh` 或 `bash install.sh` 執行，開頭要保留：

```sh
#!/usr/bin/env sh
if [ -z "${BASH_VERSION:-}" ]; then
  exec bash "$0" "$@"
fi
set -euo pipefail
```

公司 Linux 主機可能不能上網。patch install 不應做 pip install 或任何網路下載。

## 建議 release 指令

小修可用：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\release_patch.ps1 `
  -Version v1.0.4.12 `
  -Slug small-ui-fix `
  -PayloadFiles "webapp/config.py","webapp/templates/hosts.html","CHANGELOG.md","docs/release_notes/v1.0.4.12.md" `
  -ReleaseNotes "docs/release_notes/v1.0.4.12.md" `
  -TestCommand "pytest -q tests/test_app.py"
```

只驗證 TAR layout、不部署、不發 Release：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\release_patch.ps1 `
  -Version v1.0.4.12 `
  -Slug script-self-test `
  -PayloadFiles "webapp/config.py","CHANGELOG.md" `
  -SkipDeploy221 `
  -SkipRelease
```

## 小修與大修判斷

小修通常包含：

- 文字、標籤、提示語、按鈕名稱。
- CSS spacing、預設收合、欄位順序。
- 單一頁面的低風險 UI 呈現。
- 不影響資料寫入的查詢條件微調。

小修可快速流程：

1. focused test。
2. 檢查頁面或 API。
3. 打包 patch。
4. 部署測試主機。
5. `/health` 與相關頁面驗證。
6. commit / push / GitHub Release。

大修包含：

- 匯入、轉正式、批次治理、資料品質規則。
- 開門檢查、L1/L2/L3 runner、SSH/WinRM/AIX/AS400。
- 系統拓撲、核心影響圖、關聯資料。
- 權限、Token、API Key、PAM、採集帳號。
- 安裝、離線部署、MongoDB、Release layout。
- 安全、敏感資訊、debug bundle。

大修要補：

- focused tests。
- full pytest。
- 敏感資訊檢查。
- 測試主機部署驗證。
- release note。
- rollback 風險說明。

## 已知風險與下一步

優先注意：

- 大量資料頁面的預設查詢與渲染速度。
- 資產總數、可自動彙整、人工作業判斷的統計口徑要一致。
- 系統名稱正規化與別名治理，例如同義字、錯字、簡繁或常見誤寫。
- 開門檢查應只顯示可巡檢平台，不應把端點設備、網路設備、VMware host 混入巡檢候選。
- 匯入後的資產應能進入今日巡檢的候選口徑，但前提是平台、狀態、連線方式與帳號條件足夠。
- 系統關聯覆蓋明細應用搜尋式下拉，不要預設攤開全部。
- 資料品質頁的異常項目要能點進去自動過濾，並支援同類型批次套用建議。
- 文件與手冊要避免敏感資料與亂碼。

## Definition of Done

- 修改內容。
