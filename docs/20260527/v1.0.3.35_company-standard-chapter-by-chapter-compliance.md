# v1.0.3.35 公司規範逐章節對照版

日期：2026-05-27  
專案：webitgpt  
目前版本：v1.0.3.35  
用途：給公司內部 GPT、治理單位、主管或工程交接人員理解「公司結構化開發標準」與 webitgpt 現況的差距。

## 閱讀方式

這份文件是「照公司規範原文章節順序」逐章比對，不是依影響程度排序。  
結論不是 webitgpt 不遵守規範，而是 webitgpt 已是既有 Flask + MongoDB + 離線部署系統，不能用新專案範本直接硬套。

狀態定義：

| 狀態 | 意義 |
|---|---|
| 符合 | 目前做法已符合公司要求，維持即可。 |
| 大致符合 | 架構精神符合，但命名、目錄或文件格式不完全等同公司範本。 |
| 部分符合 | 有一部分符合，但仍有技術債或需漸進修正。 |
| 未完全符合 | 與公司規範有明確落差，但可分階段修。 |
| 不直接符合 | 公司規範預設情境與 webitgpt 現況不同，硬改會變成大型架構遷移。 |
| 不適用 | 該條是針對另一種技術或情境，對目前 webitgpt 不直接適用。 |

## 總體結論

webitgpt 可以把公司規範當成「新功能與後續重構目標」，但不建議立刻為了符合範本而搬目錄、重寫 API、或把 MongoDB 直接改成 SQL Server。

最安全的公司說明方式：

> webitgpt 目前是既有 Flask/Python 系統，已具備 routes/services/templates/static 分層、pytest regression tests、221 測試部署、離線安裝包與 GitHub Release 流程。公司規範可作為後續新功能的標準，但既有系統要用漸進方式補齊 OpenAPI、API response 格式、MSSQL migration design、前端模組化與安全文件，避免一次硬改造成現場部署與既有資料風險。

### DB 策略建議

建議不要只選 MSSQL 或只選 MongoDB，而是分工：

| 資料類型 | 建議 DB | 理由 |
|---|---|---|
| CMDB 主檔、資產正式資料、帳號盤點正式表、權限審核、稽核結果 | MSSQL | 公司治理、報表、權限、交易、稽核與既有企業 DB 管理較適合。 |
| nmap/NMON 原始輸出、API 分析 raw payload、匯入暫存、debug bundle、半結構化掃描資料 | MongoDB | 欄位彈性高，適合不同來源與變動格式。 |
| UI 查詢與報表 | 先讀 service 聚合結果 | 前端不應直接知道底層資料庫分工。 |

## 建議優先順序

| 優先級 | 建議事項 | 理由 |
|---|---|---|
| P0 | 禁止 PHP、禁止前端 API Key、禁止真 secret 入 Git、正式 env 覆蓋、221 測後再 release。 | 這些是安全與部署底線。 |
| P1 | 新 API 使用 `{ ok, data/error }`；補 CMDB/hosts/API Key verify OpenAPI；MSSQL migration design；高風險 route 抽 service。 | 這些最能對齊公司規範且不破壞既有功能。 |
| P2 | README/docs index、`.env.example` 強化、前端 inline handler 漸進拆分、CSS 元件化。 | 提升交接與可維護性，但不應阻塞現場修復。 |
| P3 | 全域格式化、全面 TypeScript、目錄硬搬成公司範本、改寫 Node.js。 | 成本高、風險大，短期沒有必要。 |

## 對公司可以這樣說

webitgpt 已符合「禁止 PHP、後端代理 API Key、基本分層、測試與文件交付」等核心要求。  
尚未完全符合的是「OpenAPI 全覆蓋、API response 統一、正式 DB 預設 MSSQL、前端完全模組化、README/env 統一模板」。  
這些差距不是不能做，而是必須以既有系統相容性為前提，採「新功能先符合、舊功能分階段補齊」策略。

最不建議的做法是為了表面符合規範，立刻把 Flask 專案改成 Node.js、把 MongoDB 全部搬到 MSSQL、或把所有 API response 一次改掉。這會讓現場部署、離線移植、既有資料與測試全部同時承擔風險。
